# Статус миграции жизненного цикла заказов

Дата актуализации: 14 июля 2026.

## Текущее состояние

- Код подготовлен в ветке `codex/fix-order-lifecycle`.
- Новая схема **ещё не применена** к боевому Supabase.
- Новый Apps Script **ещё не развёрнут**; действующий `SYNC_URL` продолжает обслуживать текущую версию.
- Боевые RLS, PIN и авторизация Apps Script не менялись.
- `supabase/supabase-schema.sql` — безопасный no-op для совместимости. Схему нужно обновлять только файлами из `supabase/migrations/` по порядку.

## Что готово

- Один номер заказа хранится как одна аренда. Повторяющиеся строки Google Sheets объединяются: минимальная дата выдачи, максимальная дата возврата.
- Выдача и возврат фиксируются отдельно для каждого заказа. После выдачи заказ больше не может стать новой выдачей и ожидает только возврата.
- Запись, удаление, привязка визита, черновики и закрытие смены выполняются атомарными RPC.
- Повторная отправка одного `clientEventId` идемпотентна; удалённое событие защищено tombstone-записью и не воскресает из старого черновика.
- Серверные ошибки видны пользователю. Только временные ошибки остаются в очереди повторной отправки.
- Сверка показывает непривязанные визиты и нарушения жизненного цикла.
- Для привязки доступны все совместимые активные заказы, включая заказ с будущей датой: менеджер больше не упирается в текущий список нарушений.
- Четыре заказа из двух старых неоднозначных визитов изолированы от заданий кладовщика и показаны в «Сверке» только как отчёт: система не угадывает их операцию.
- Уже выданная аренда продолжает ожидать возврата, даже если её строка исчезла из следующего экспорта Google Sheets.
- Дашборд получает согласованные snapshot-данные и правильно показывает выданные, возвращённые, однодневные и просроченные заказы.
- Старое скрытие через `orders.deleted_at` переносится в `manual_hidden`, поэтому скрытый заказ не появится снова после миграции.

## Резервные копии и dry-run

- Полная копия от 13.07.2026: Google Sheets в XLSX, Supabase в JSON, активный Apps Script.
- Перед выкладкой 14.07.2026 снят атомарный read-only snapshot Supabase одним SQL-запросом: 198 заказов, 225 визитов, 247 связей визит–заказ, 30 смен, 4 черновика. Копия включает каталог текущей схемы и контрольные суммы файлов.
- Миграции воспроизведены локально на этой копии PostgreSQL: 225 → 173 визита, удаляются ровно 52 подтверждённых технических повтора.
- Сохраняются 2 неоднозначных смешанных визита и 2 спорные выдачи заказа `26-A-001599`.
- Все 4 заказа из неоднозначных визитов остаются видимыми менеджеру, но не могут случайно стать новой выдачей/возвратом у кладовщика.
- Единственный ранее скрытый заказ остаётся скрытым.
- Три визита из старых серверных черновиков однозначно связаны с существующими событиями и получают стабильные идентификаторы.

Подробности: `reports/data-repair-dry-run-2026-07-13.md` и `reports/order-lifecycle-implementation-2026-07-14.md`.

## Проверка

Автоматические тесты: **72 из 72 пройдены**.

Проверены:

- ключевой переход `к выдаче → выдан → к возврату → возвращён`;
- запрет повторной выдачи на следующий день;
- ожидание возврата после исчезновения выданного заказа из нового экспорта;
- идемпотентность повторной отправки и tombstone после удаления;
- восстановление очереди и черновиков после перезапуска;
- атомарное резервирование одной активной смены на кладовщика, включая первый запрос после офлайна;
- постоянный конфликт двух устройств с отдельным сохранением локальной смены и безопасным ручным объединением;
- закрытие смены на другом устройстве и перенос только действительно неподтверждённых визитов;
- конкурентные удаления, закрытие смены и устаревшие ответы;
- объединение дублей Google Sheets и строгий разбор дат;
- сохранение старого soft-delete и аварийный откат cleanup при несовпадении контрольного количества;
- карантин неоднозначных исторических операций до ручной сверки;
- migration dry-run на снимке боевых данных;
- сверка с будущими совместимыми заказами, дашборд, журнал и CSV.

## Порядок боевой выкладки

1. До окна переключения создать **новое**, пока не используемое развёртывание Apps Script из `supabase/apps-script-sync.js`; старый deployment не обновлять на месте.
2. Согласовать слияние ветки и короткое окно без записей. Попросить кладовщиков завершить текущие действия, закрыть или обновить старые вкладки и не открывать новые смены до окончания проверки.
3. Уже внутри write-freeze снять свежий атомарный Management API snapshot. Последовательный REST fallback разрешён только с флагом `--allow-sequential`.
4. Применить `202607120000_base_schema.sql` и `202607130001_order_lifecycle.sql` без cleanup-миграции.
5. Снять транзакционный JSON-снимок через новый `warehouse_backup_snapshot`, затем сравнить dry-run с ожидаемыми 52 удалениями.
6. Применить `202607130002_remove_confirmed_retry_duplicates.sql`. Миграция откатывается целиком, если контрольные данные изменились или удаляется не ровно 52 либо 0 строк при повторном запуске.
7. Проверить количества, спорные записи и RPC на боевой базе.
8. Одновременно включить новый контур: записать новый URL в `config.js`, слить ветку и дождаться публикации GitHub Pages. До этого write-freeze не снимать.
9. Принудительно обновить открытые страницы, выполнить `syncOrders`, затем smoke-тест одного тестового цикла `выдача → возврат` и сверки.
10. Снять write-freeze и обновить отчёт PR только после успешной проверки.

Старый Apps Script и старые открытые вкладки после структурной миграции использовать нельзя: они пишут в старом формате и обходят новые атомарные проверки.
